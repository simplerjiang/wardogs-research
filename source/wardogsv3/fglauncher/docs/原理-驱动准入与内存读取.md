# 原理说明：驱动准入链路与物理内存读取

> 文档性质：本地实验记录的**原理说明**，配套工程 `E:\wardogsv3\fglauncher`。
> 所有实验对象为本机沙箱内的自有进程与本地样本；文中出现的地址、哈希、RVA 均来自本机实测日志。
> 本文只描述"系统做了什么、我们观察到什么、代码在哪一行"，不承担教学以外的用途。

## 0. 术语与角色（先把名字说清楚）

| 本文用词 | 指什么 | 谁写的 |
| --- | --- | --- |
| **宿主** | `WardogLauncher.exe`，唯一入口程序，负责全部流程与日志 | 本工程 |
| **中转驱动** | `PGRHostControl.sys`（34 KB，sha256 `076cfa7d…f720a4`），参照样本原件的**逐字节副本** | 非本工程 |
| **载荷驱动** | `WardogProbe.sys`（3.5 KB，未签名），用来验证"加载链是否真的通了" | 本工程 |
| **准入判定点** | 系统在内核映像载入流程中执行的一致性校验代码（下文 §3 定位方法） | 系统组件 |
| **地址空间** | 某个进程的页表根（CR3 指向的四级页表） | 系统组件 |
| **物理页映射** | 中转驱动提供的能力：把"物理地址 → 本进程可读写的指针" | 中转驱动 |

下文 §2 会展开。

## 2. 职责边界：中转驱动为什么不负责"加载"

中转驱动对外只暴露两个操作：

| 操作 | 语义 |
| --- | --- |
| `0x80102040` | 输入一段物理地址与长度，返回一个**本进程可读写的指针** |
| `0x80102044` | 解除上一步建立的映射 |
| `0x0022218C` | 握手（版本/能力协商） |

它不知道"进程"、"虚拟地址"、"文件"、"映像"这些概念。因此：

* 它**不会**去读 `WardogProbe.sys`；
* 它**不会**调用任何加载例程；
* 它**没有**任何参数可以指定一个文件名。

把"虚拟地址"翻译成"物理地址"、把目标进程的页表找出来、把某个映像载入内核——这些都在
用户态由本工程的 `translate.cpp` / `target.cpp` / `service.cpp` 完成。中转驱动只是那一步
"物理页 → 我能读写的内存"的提供者。

> 一句话：**能力是借的，机制是自己写的。**

## 3. 系统自己的映像载入流程（背景知识）

一个内核映像从"磁盘上的文件"变成"运行中的驱动"，系统的路径是固定的一条：

```
用户态：写入服务项（Type/Start/ImagePath）
        → NtLoadDriver(服务名)
内核态：IopLoadDriver
        → MmLoadSystemImage（读文件、按 PE 头映射、重定位）
        → 一致性校验（镜像哈希与信任链判定）
        → 通过 → 调用 DriverEntry；不通过 → 返回 0xC0000428
```

未签名映像在这一步会被拒绝，返回值是 `STATUS_INVALID_IMAGE_HASH (0xC0000428)`。
本工程的"对照实验"正是用这个返回值当基线：**基线必须被拒绝**，否则后续结论不可归因（见 §5）。

### 3.1 判定点是怎么被定位的（纯静态分析）

`src\ci.cpp:37-81` 的做法不依赖任何硬编码地址：

1. 从磁盘 `ntoskrnl.exe` 的导出表按**名字**取三个例程的 RVA：
   `PsSetLoadImageNotifyRoutine`、`PsSetLoadImageNotifyRoutineEx`、`PsRemoveLoadImageNotifyRoutine`；
2. 在它们的函数体里搜索指令形状 `F0 0F BA 2D`（即 `lock bts [rip+disp32], imm8`，
   代码里写作 `needle = 0x2DBA0FF0`）；
3. 把该指令后面的 RIP 相对偏移解出来 → 得到它操作的**标志字 RVA** 与**位号**。

本机实测解出的结果：

| 项 | 值 |
| --- | --- |
| 例程体 RVA | `0x787850` |
| 相邻例程 RVA | `0xAC30F0` |
| 标志字 RVA | `0xFD9A88`，位号 `0` |
| 现场例程体字节 | `48 83 EC 28 33 D2 E8 45…`（`sub rsp,28h; xor edx,edx; call …`） |
| 现场标志字值 | `0x1F` |

**这就是"哪个位置改"的唯一答案**：不是某个常量，而是运行时按"导出名 + 指令形状"算出来的
两处（一个函数体、一个标志字），并用案例文件里的钉值交叉校验（`gate.routine_rva` / `gate.flag_rva`）。

## 4. 两类"改变"，性质完全不同

初学者最容易混淆的是"到底改了谁"。这里把两类改动分清楚：

| 类别 | 位置 | 内容 | 性质 | 代码位置 |
| --- | --- | --- | --- | --- |
| **配置类** | 注册表服务项 | `ImagePath = \??\…\WardogProbe.sys` | 系统公开接口，正常配置，**不改内核任何代码** | `src\service.cpp:55-57` |
| **实验类** | 内核映像内 2 处 × 4 字节 | 函数体写 `48 31 C0 C3`（`xor eax,eax; ret`）；标志字写 `0` | 临时改动，**用完立刻还原** | `src\main.cpp:675/680/696/733` |

要点：

* 载荷驱动 `WardogProbe.sys` **一个字节都没有被改**，它由内核加载器按它自己的 PE 头映射、
  由内核调用它的 `DriverEntry`；
* 中转驱动 **一个字节都没有被改**；
* 唯一被写的是内核里那 8 个字节，且**在同一个函数里完成"保存 → 写入 → 校验 → 还原"**。

## 5. 实验流程（`--mode run`）

```
① 对照 A：先请求载入载荷驱动
   → 期望 0xC0000428。若"竟然通过了"，直接终止（退出码 11：本机未强制校验，结论不可归因）

② 保存原值：读取两处目标的现有 4 字节，连同 VA 一起写入日志
   事件 original_content_saved

③ 写入临时值：ci::WriteBytes，然后立刻读回比对
   事件 temporary_content_written，字段 match=true/false

④ 窗口期请求：同一个服务项再请求一次载入
   验证"真的跑起来了"：QueryDosDeviceW 能看到 \DosDevices\WardogProbe
   事件 followup_load_begin / followup_load_result

⑤ 还原：把第 ② 步保存的字节原样写回，再次读回比对
   事件 restore_begin / restore_result

⑥ 对照 B：再请求一次载入
   → 期望重新被拒（证明第 ④ 步的成功确实来自第 ③ 步的临时改动，而不是别的原因）
```

退出码：`0` 全链成立；`10` 定位阶段失败；`11` 基线竟然通过；`13` 拒绝写入（**默认行为**）；
`14/15/16/17` 依次对应"载入失败 / 驱动未真正运行 / 未还原 / 还原后仍能载入"。

> **默认只读**：不显式给 `--allow-write` 时，流程在第 ③ 步之前就退出（事件 `write_refused`，
> 退出码 13）。也就是说，正常情况下它只做到"读出现场字节 + 打印将要写入的内容"。

## 6. 读取链路（这条链完全是我们自己实现的）

### 6.1 物理地址 → 字节

`translate.cpp` 的 `ReadPhys → ReadPage / ReadVa`：先按四级页表把 VA 拆成
`PML4E → PDPTE → PDE → PTE`，逐级读表，最后得到物理地址，再通过能力层读出字节。
四级都支持 1 GB / 2 MB 大页的掩码运算。

### 6.2 找到"内核地址空间"

整机物理内存按"RAM 区间"分批扫描（本机三段：`0x1000-0x9F000`、`0x100000-0x80000000`、
`0x100000000-0x840000000`），对每个 4 KB 页做便宜的结构判定，收集候选页表根；
再用"从该根遍历内核映像基址、读到的头必须与磁盘内核的 `SizeOfImage` + `TimeDateStamp` 一致"
来确认。**只有跨越真实 RAM 的读，绝不触碰 MMIO 区间。**

### 6.3 找到"目标进程地址空间"

受保护客户端会拒绝用户态探测（实测：`ReadProcessMemory` 返回失败、模块枚举返回 `win32=5`），
因此定位做四级降级，前一级失败自动降级：

| 级 | 手段 | 依赖 |
| --- | --- | --- |
| 1 | 命令行/案例直接给基址（`--base`） | 无 |
| 2 | 内核进程链：`PsInitialSystemProcess` → 活动进程链 → 名称+PID → 页表根 | 内核地址空间可读 |
| 3 | 直接给页表根（`--cr3`） | 需先取得 CR3 |
| 4 | **用户半区头扫描**：遍历每个内核根页表的用户半区，对 2 MB 区按 64 KB 步长探测 PE 头，用磁盘指纹校验 | 只需候选根集合 |

> 实测反例值得记下：`K32GetMappedFileNameW` 返回的基址在该进程自己的页表里**没有映射**
> （`read_unmapped`），是受保护客户端给出的**假基址**；只有内核侧（级 2 / 级 4）得到的基址
> 才能走到真实镜像。这类"用户态元数据不可信"的现象，是本工程坚持用驱动侧定位的原因。

### 6.4 读取结果怎么自证

三条互相独立的证据：

1. **磁盘指纹**：镜像头读出的字节与磁盘文件同一 RVA 的字节逐字节比较（`matches_disk=true`）；
2. **页内偏移算术**：同一地址 `+0`、`+8`、`+0x1000` 三处应落到同页/相邻页的物理地址；
3. **双地址空间交叉**：同一 VA 在目标页表与内核根页表下各自遍历一次。

受保护程序的代码段与磁盘不同属于正常（运行时解包），日志里记为 `read_differs_from_disk`，
不计为失败；判定口径是"至少有一条证据成立且无矛盾"。

## 8. 边界与工程约束

| 约束 | 落实方式 |
| --- | --- |
| 默认不写内核 | 无 `--allow-write` → 第一次写之前退出（`write_refused`，退出码 13） |
| 不触碰设备内存 | 所有物理读都限制在 RAM 区间（band 判定），MMIO 一律拒绝 |
| 临时改动必还原 | 保存/写入/还原在同一函数内顺序执行，每步读回校验，失败即中止 |
| 无网络、无持久化 | 全流程不联网；服务项用 `WardogLaunch_<pid>_<tick>` 临时键，结束即删 |
| 失败可归因 | 基线对照 + 反向对照 + 明确退出码，任何异常都不产生"看起来成功"的结论 |
| 样本完整性 | 中转驱动加载前核对整文件 sha256，不匹配即拒绝运行 |

## 9. 已知局限

* 内核进程链在个别情况下会在某一级页表读到指向 RAM 之外的条目而中断，这属于**观测不完整**，
  不是"被拦截"；级 4 的用户半区头扫描是目前更稳的兜底路径。
* 若目标机器开启 HVCI/VBS（本机未开启），物理页受 SLAT 的 W^X 约束，本方案的"改只读代码页"
  思路未必成立——这一点在文档里如实标注，不做推广性结论。
* 载荷驱动只用于证明加载链成立（创建 `\Device\WardogProbe` 后被用户态观察到），
  它不承担任何业务功能。
