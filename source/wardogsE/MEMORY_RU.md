# Как устроено чтение памяти

Снаружи это выглядит как «чит видит игроков». Внутри — четыре звена: маппинг драйвера, IOCTL-протокол, копирование в ядре и слой в юзермоде, который превращает байты в мировые координаты.

---

## 1. Почему не ReadProcessMemory

`ReadProcessMemory` из нашего процесса — это открытый handle на игру плюс вызов, который античит видит тремя разными способами: handle-таблица, ETW-провайдер, перехваченный `NtReadVirtualMemory`. Один такой вызов = флаг.

Поэтому чтения вообще нет в юзермоде. Процесс читает **свой драйвер**, а драйвер читает игру из кольца 0. У нашего процесса нет ни handle на `Wardogs.exe`, ни единого вызова `ReadProcessMemory` в IAT — только `NtDeviceIoControlFile` на собственное устройство.

---

## 2. Маппинг: как драйвер попадает в ядро

`START.bat` → UAC → `kd2.exe`.

`kd2.exe` — форк kdmapper. Внутри у него в ресурсах лежит подписанный уязвимый драйвер Intel, через который он снимает DSE и маппит в память ядра наш образ. Наш образ — файл `kernel-mode.sys` **из папки самого kd2.exe** (путь зашит, см. `BUILD_RU.md`). Никакого `sc create`, никакой записи на диск: образ живёт в non-paged pool, в списке загруженных драйверов его нет.

Дальше `DriverEntry`:

- создаёт `\Device\AbiComm` с SDDL (system — полный, admins/world — RW);
- создаёт симлинк `\??\AbiComm`;
- считает ключ сессии;
- пишет его в `HKLM\SYSTEM\AbiComm\SessionKey`.

Устройство создаётся через `IoCreateDriver`, а не через обычную загрузку — это вне зоны PatchGuard.

---

## 3. Ключ сессии

Драйвер читает `BootId` из `\Registry\Machine\SYSTEM\CurrentControlSet\Control\Session Manager\Memory Management\PrefetchParameters`, считает `Xorshift(BootId ^ 0x8F2A9C4B)` и получает `SessionKey`.

Ключ **меняется каждый бут**. Клиент при старте вычитывает его из `HKLM\SYSTEM\AbiComm\SessionKey` и подставляет в каждый IOCTL.

Смысл: послать IOCTL «наугад» нельзя. Драйвер сверяет `magic_key` в каждом запросе и на несовпадении возвращает `STATUS_INVALID_PARAMETER` (не падает, не логирует — просто отказ). Статический сканер, который нашёл устройство, без ключа не прочитает ни байта.

---

## 4. Протокол: один IOCTL = один диапазон памяти

Устройство открывается через `NtCreateFile` из ntdll, а не через `CreateFileW`: меньше видимых импортов и нет разбора Win32-путей. Клиент перебирает `\Device\AbiComm0` … `AbiComm4` — на случай, если имя занято после предыдущего маппинга.

Формат запроса — `ABI_COMMAND`, 24 байта, `#pragma pack(1)`:

```
ULONG     magic_key;    // ключ сессии
ULONG     process_id;   // PID игры, известен заранее
ULONG_PTR address;      // куда смотреть
SIZE_T    size;         // сколько байт
```

Четыре кода:

| IOCTL | Код | Что делает |
|---|---|---|
| READ | `0x222004` | копирует `size` байт из игры в наш буфер |
| GET_BASE | `0x222008` | читает `PEB->ImageBaseAddress` (peb + 0x10) |
| UNLOAD | `0x22200C` | удаляет симлинк, устройство становится недоступным |
| WRITE | `0x222010` | пишет в игру (нужен чамсам) |

Транспорт — `METHOD_BUFFERED`. Тонкость, на которой легко обжечься: при `inputLength < outputLength` ядро берёт SystemBuffer из **выходного** буфера. Поэтому на чтении мы отправляем 24 байта команды, а получаем прямо в свой буфер — данные приходят без промежуточной копии. На записи наоборот: input длиннее output, и в один буфер укладывается команда + payload.

Ограничения в драйвере, все проверяются до копирования:

- `size` от 1 до `0x10000` (64 КБ);
- `size` не больше длины выходного буфера;
- `magic_key` совпадает с ключом сессии;
- весь диспетчер обёрнут в `__try/__except` — битый указатель возвращает код исключения, а не роняет систему.

`GET_BASE` экономит целую ветку: база модуля берётся из PEB процесса, а не перебором модулей из юзермода.

## 5. Что происходит в ядре при чтении

```
ReadTargetMemory(pid, addr, kernelBuf, size)
  ├─ PsLookupProcessByProcessId(pid) → PEPROCESS
  ├─ MmCopyVirtualMemory(game, addr, current, kernelBuf, size, KernelMode)
  └─ ObDereferenceObject(process)
```

`MmCopyVirtualMemory` — штатная функция ядра, которой пользуется и сам Windows. Она сама поднимает нужные страницы, разбирается с нерезидентными (ушедшими в pagefile), корректно обрабатывает guard-страницы и не оставляет процесс присоединённым, если внутри случилось исключение.

Почему не `KeStackAttachProcess` + `memcpy`: attach оставляет систему в подвешенном состоянии при любой ошибке внутри копирования, а `memcpy` по нерезидентной странице — это багчек. `MmCopyVirtualMemory` делает то же самое, но с обработкой всех этих случаев.

Если скопировалось меньше запрошенного — возвращается `STATUS_PARTIAL_COPY`. Для клиента это значит «страница не отмаплена»: объект выгружен или уже освобождён.

Ключевой момент про античит: `MmCopyVirtualMemory` берёт реальные таблицы страниц из `EPROCESS`. Любые трюки уровня Ghost CR3 (подмена CR3 в юзермоде, чтобы спрятать память от сканера) на kernel-чтение не действуют — оно идёт мимо юзермодного адресного пространства.

## 6. Юзермод: тонкий слой поверх IOCTL

Вся работа с памятью сводится к пяти функциям:

```c
static int rd   (uint64_t a, void* o, size_t sz);  // базовый вызов
static uint64_t rd64(uint64_t a);   // 8 байт
static uint32_t rd32(uint64_t a);   // 4 байта
static float    rdf (uint64_t a);   // float
static double   rdd (uint64_t a);   // double
```

`rd` не бросает исключений и не логирует: он возвращает 0, а значение-ноль в поле `out` означает «не прочиталось». Поэтому **каждый** результат, который используется как указатель, проходит через `pl()`:

```c
static int pl(uint64_t v){ return v >= 0x10000ULL && v < 0x00007FFFFFFFFFFFULL; }
```

Это дешёвая, но обязательная страховка: без неё один освобождённый актор превращается в цепочку чтений по мусорным адресам — кадр дёргается, маркеры улетают в бесконечность. `pl()` отсекает и нули, и ядровые адреса, и мусор из переиспользованной памяти.

Кэшируется ровно три вещи, каждая по своей причине:

- **указатель на `UWorld`** — живёт 5 секунд, иначе поиск шёл бы по миллионам адресов каждые 8 мс;
- **карта костей** (`BONEMAP` по `USkinnedAsset`) — считается один раз на модель, потому что имена костей одинаковы у всех игроков;
- **список сущностей** — двойной буфер, публикуется под критической секцией.

## 7. Что и с какой частотой читается

Поток чтения (`ReadThread`) крутится с `Sleep(8)` и `timeBeginPeriod(1)` — примерно 120 Гц. Без поднятого таймера `Sleep(8)` на деле спит 20–25 мс, и маркеры отстают от тел на целый период.

Такт устроен так:

| Что | Как часто |
|---|---|
| роспись игроков (`PlayerArray`) | каждый тик |
| локальный пешка, камера, FOV, отдача | каждый тик |
| позиции и здоровье сущностей | каждый тик |
| скелеты | каждый тик, но только для тех, кто ближе `eff_skel_dist()` |
| глубокий обход 4600 акторов | раз в 40 тиков (~320 мс) |
| поиск `UWorld` | раз в 150 тиков (~1.2 с) и при провале пробы |

Цепочки указателей, по которым это всё достаётся:

```
UWorld
 ├─ +0x1B0 GameState
 │    └─ +0x2D0 PlayerArray → [i] APlayerState
 │         ├─ +0x330 Pawn
 │         └─ +0x360 PlayerNamePrivate
 └─ +0x228 GameInstance
      └─ +0x38 LocalPlayers[0]
           └─ +0x30 PlayerController
                ├─ +0x360 Pawn (мой)
                ├─ +0x2C0 PlayerState
                └─ +0x370 CameraManager → +0x1560 CameraCache → +0x10 POV
```

Дальше от пешки: `+0x1C0` корневой компонент (мировая позиция), `+0x3A0` меш, `+0x748` компонент живучести, `+0x780` оружие, `+0x758` инвентарь.

**Скелет — это один IOCTL, а не 400.** Массив трансформов читается целиком: `(последний_нужный_бон + 1) * 0x60` байт, максимум 64 КБ. Самая тяжёлая модель — 583 кости, это ~55 КБ, то есть влезает в один вызов с запасом. Раньше на каждую кость шёл отдельный IOCTL, и при 80 игроках скан не успевал закончиться до отрисовки — отсюда была рябь, тем сильнее, чем больше народу в рейде.

Кости читаются в **компонентном** пространстве (сырые значения вокруг центра модели), поэтому к ним применяется `ComponentToWorld`, иначе скелет рисуется в нулевой точке карты.

## 8. Цена

- Один IOCTL — синхронный переход в ядро и обратно, единицы микросекунд. На 80 игроков с ближними скелетами это тысячи вызовов в секунду.
- Счётчики встроены: `perf.txt` в папке чита пишет `ioctl/s`, `bytes/s` и разбивку по источникам (`span`, `relloc`, `bones`, `wep`, `sweep`, `parr`, `findw`). По нему видно, какая часть скана жрёт вызовы.
- `PsLookupProcessByProcessId` вызывается на **каждое** чтение, без кэша `PEPROCESS`. Это осознанный размен: кэш пришлось бы валидировать на каждом вызове, а разница в стоимости — доли микросекунды против риска прочитать освобождённый процесс.
- Отрисовка после переноса на GPU — 120–125 fps при ~14.4% одного ядра. Чтение памяти идёт отдельным потоком и в кадр не попадает.

## 9. Когда чтение «не работает» — что это значит

| Симптом | Причина |
|---|---|
| `rd` возвращает 0 на всё | неверный ключ сессии — проверь `HKLM\SYSTEM\AbiComm\SessionKey` |
| пустые маркеры при живом процессе | оффсеты устарели после патча игры |
| часть полей нулевая, часть нормальная | `STATUS_PARTIAL_COPY`: страница выгружена, объект мёртв |
| скелет застыл, позиции живые | читается LOD-кэш костей вместо живого массива |
| `0xC000009A` при маппинге | блок уязвимого драйвера (HVCI / blocklist / Defender) |
| `0x109` в BSOD | повторный маппинг в тот же бут — PatchGuard |

---

## 10. Что видно снаружи

Наш процесс не открывает игру, не читает её память и не грузит драйвер через SCM. Видно другое:

- в Object Manager появляется `\Device\AbiComm` — объект существует, хоть и без записи на диске;
- в ядре лежит образ без модуля в списке загруженных (mapped, не loaded) — палится сканированием `SystemBigPoolInformation` и сверкой с `PsLoadedModuleList`;
- IOCTL-трафик на наше устройство виден любому, кто поставит фильтр на `IRP_MJ_DEVICE_CONTROL` — ключ сессии мешает прочитать чужое, но не скрывает факт общения;
- ETW-провайдер Threat-Intelligence ловит загрузку уязвимого драйвера до того, как он что-то сделал.

То есть скрытность здесь держится не на «невидимости», а на том, что нет ни одного юзермодного признака, по которому античит ищет обычно: handle на игру, `ReadProcessMemory`, модуль в списке, файл на диске.

---

## 11. Быстрая проверка, что чтение живо

1. `1_run\tools\drvping.exe` — открывает устройство, читает ключ из реестра, делает пробное чтение.
2. `perf.txt` — если `ioctl/s` больше нуля и `ents` растёт, чтение идёт.
3. Если `drvping` не открывает устройство — драйвер не смаплен: перезагрузка и заново `START.bat`.
